# Contributing

Contributor guide: paths, conventions, tool inventory. Applies to the whole tree.

## What this repo is

A **reverse-engineering analysis project**, not application source code. It documents:

1. **`DELTARUNE.exe`** — the native executable shipped with DELTARUNE (Steam). This is
   **not** game logic; it is the **GameMaker Studio 2 "VC_Runner" runtime** (the YoYo
   Games VM interpreter). The RE docs here describe the *engine*.
2. **The decompiled GML** of the game itself (from the companion `data.win`), dumped as
   ~1,300 `.gml` files under `code/`.

Binary identity: x86-64 PE32+, image base `0x140000000`, ~9.25 MB,
MD5 `7bf3cccc2e54481ced3a149e1a083684`. GameMaker runtime `2022.0` (per the root
`data.win` offset map).

| `<windows-drive>` | `/dev/nvme1n1p3` | `C:\` | the Windows system drive — `Program Files`, incl. the Windows IDA install |

|---|---|

ever remaps, the docs' `E:` prefixes are what to update; the Linux mounts
(`<data-drive>`, `<windows-drive>`) are stable.

Files present in the game install dir (all readable here):

- `DELTARUNE.exe` — the runtime this project analyzes.
- `DELTARUNE.exe.i64` — the ~108 MB reference IDA database. This is the real source of
  truth for the RE; everything else exe-side is derived from it.
- `DELTARUNE.exe.json` — an export of the IDB (names/types/etc.).
- `DELTARUNE.pdb` — **not** a Microsoft-shipped PDB. It is **generated by FakePDB from
  the IDB** (`Edit → FakePDB → Generate .PDB file`), so its symbols are exactly the
  IDA names/types this project produced, re-exported for consumption by
  x64dbg / WinDbg / Ghidra / a live debugger. Downstream artifact of the RE, not an
  input. FakePDB is **installed into the Windows IDA** at
  `<windows-drive>/Program Files/IDA Professional 9.1/plugins/fakepdb/` (backend
  binaries in `windows_amd64/`: `fakepdb_pdb.exe`, `fakepdb_pe.exe`, `fakepdb_coff.exe`);
  a user-modified copy of its source is also at
  `<projects>/fakepdbStuff/FakePDB/`. Linux user plugins are also installed at `~/.idapro/plugins/fakepdb.py`
  and `~/.idapro/plugins/fakepdb/`, with native `linux_amd64/` backends.
  Headless loading and PDB export were verified on 2026-09-06 using the idalib Python
  environment and a temporary IDB copy; see [01_methodology.md](01_methodology.md#linux-fakepdb-headless-verification-2026-09-06).
- `data.win` (~2.95 MB) — the **chapter-select launcher only** (see below).
- `data.win.offsetmap.txt` — UndertaleModLib offset map of **that launcher `data.win`
  only**, not of any chapter. It spans the whole ~2.95 MB file: 3 rooms
  (`PLACE_CHAPTER_SELECT*`, `room_restart_true`), ~237 scripts that are OS-shim /
  title-select glue (`ossafe_*`, `scr_switch_title`, demo/full-title helpers), 16
  sprites, 18 sounds. The ~595 "chapter" hits are just the select-menu's unlock UI.
- `chapter{1..5}_windows/` — each holds its **own** `data.win` with the actual game
  content: ch1 13 MB, ch2 67 MB, ch3 126 MB, ch4 132 MB, ch5 165 MB. **None of these
  has an offset map or its own IDB in the install.**
- `mus/`, `options.ini`.

> The `code/` GML dump is chapter content (`scr_gamestart`, `global.hp[]`, combat
> scripts), so it was decompiled from one of the `chapter*/data.win` files — almost
> certainly **chapter 1** (party = Kris/Susie/Ralsei, Ralsei maxhp 70) — **not** from
> the launcher `data.win` that `data.win.offsetmap.txt` describes. The two do not
> correspond.

This directory is **not a git repository**. There is no build, no test suite, no CI.
"Work" here means reading/writing Markdown analysis, curating the GML dump, and
maintaining the Cheat Engine tooling.

## Conventions — follow these when editing

These come from `01_methodology.md` and are the standard the existing docs hold to.

- **Evidence over inference.** Names and identities are anchored to hard evidence:
  string literals the runtime passes to its own `Function_Add`, unique error-format
  strings, decompiled field offsets. Do not introduce a name or claim that isn't
  traceable to something in the binary or the GML dump.
- **Leave the unknown unknown.** If a function's purpose isn't established, it stays
  `sub_xxxxxxxx`. Flag "needs further analysis" explicitly rather than guessing.
- **Call out unconfirmed data.** Where an offset/size/value could not be confirmed from
  decompilation, say so inline (see `05_data_structures.md` for the tone).
- **Hex is verbatim.** Addresses and hex values are copied exactly as IDA / Hex-Rays
  printed them. Keep the `0x140......` form and the image base `0x140000000`.
- **No manual base math.** Project constraint: delegate every number-base conversion to
  tooling. Don't hand-convert hex↔dec in prose.
- **`gml_` prefix** for GameMaker builtins (avoids collisions with CRT symbols like
  `abs`, `sin`, `round`). Runtime primitives get descriptive names (`YYGetUint32`,
  `Variable_GetValue`, `Array_GetElement`, …).
- **Cross-link docs** with relative Markdown links, e.g.
  `[03_rvalue_type_system.md](03_rvalue_type_system.md)`.
- **Mark verified findings** with a `CONFIRMED:` lead-in when a claim is proven from the
  GML dump or decompilation (pattern already used in `07_...md`).
- Keep tables GitHub-flavored Markdown; keep the numbered-doc filename scheme.

## Working with the binary (IDA)

**IDA Pro 9.1 is installed on both platforms:**

- Linux: `~/ida-pro-9.1/` — has `idalib/`, `libidalib.so`, `idapyswitch`, and a
  valid `idapro.hexlic`. IDA's **idalib** runs *here*, headless,
  against `DELTARUNE.exe.i64` — no GUI needed.
- Windows: `<windows-drive>/Program Files/IDA Professional 9.1/` (= `C:\Program Files\…`)
  — the full Windows GUI install. **FakePDB is installed on both platforms**
  (Linux uses the user plugins directory; see above).

Without IDA at hand, work from the committed
docs, the GML dump, and `gml_builtins_manifest.json`; don't fabricate decompiler output.

The reference IDB lives with the game install
(`<steam-library>/steamapps/common/DELTARUNE/DELTARUNE.exe.i64`, ~108 MB),
not in this folder, and both IDA installs open it off the shared drive. Renames /
types / comments made there land in that IDB and are not otherwise tracked here —
reflect any durable finding back into the relevant `0X_*.md` doc.

**Usage notes for this project:**

- **Frida + wine** is the way to instrument `DELTARUNE.exe`: run it under `wine` and
  attach Frida to the wine process (Linux-native Frida can't hook the PE directly).
  Highest-value target: hook `Function_Add`, dump live `global.*`
  `var_id`→name→value pairs, and validate the `07_...md` memory model dynamically. The
  `cheatengine/` Lua is the Windows-side stand-in for the same job.
- **UTMT CLI** re-dumps GML / offset maps from any chapter's `data.win`. It **blocks on
  stdin** — always invoke with `< /dev/null`. `utmtcli info <data.win>`,
  `utmtcli dump <data.win> ...`, or drive it with a C# script via `utmtcli load`.
- Still missing for patch distribution: `xdelta3` / `bsdiff`
  (`sudo pacman -S xdelta3`; `bsdiff` is AUR).

## The GML dump (`code/`)

- Decompiler output from `data.win` — filenames are `gml_GlobalScript_<script>.gml` and
  `gml_Object_<object>_<Event>.gml`. Names like `arg0`, `__txtcolor__` are
  decompiler-synthesized.
- Treat as **read-mostly reference**. It's the ground truth for what game variables
  mean (e.g. `global.hp[1]` = Kris's HP, proven in `scr_gamestart`). If you re-dump or
  extend it, keep the flat `code/` layout and the filename scheme.

## Cheat Engine tooling (`cheatengine/`)

`deltarune_stats.lua` walks the global variable hashmap at `g_pGlobalObject + 72`,
locks each variable's `var_id`, and re-resolves addresses every tick (fixed pointer
paths are fragile because the hashmap rehashes). If you extend it, follow the
`discover()` / `resolveAll()` pattern documented in `cheatengine/README.md` and keep
scalars vs. arrays handled the way `gold`/`tension` vs. `hp`/`maxhp` already are.

## Scope / etiquette

- This is authorized RE for interoperability, documentation, and single-player cheat
  tooling. Keep additions in that spirit.
- Don't add a build system, reformat existing docs wholesale, or rename the numbered
  files without being asked.
- Prefer editing the existing doc that owns a topic over creating a new top-level file.
